# Invar 新会话启动词：AI 可复现工程连续工作协议

你现在接管的是 Windows 项目 `C:\dev\Invar`。这是一个已经进行过多轮源码考古、1:1 行为迁移、TDD 重构和 Rust/Python 双引擎架构演进的长期工程。你不是从零开始，也不能把当前工作当成一次性的代码生成任务。

## 一、先继承当前工程背景

项目目标是构建一个可复现、可审计、可扩展的 AI 研究与软件系统工程骨架。当前重点是 Web API 逆向/契约推导/安全研究闭环，但这套技术要抽象为可迁移到其他 AI、Agent、模型、推理引擎、桌面应用、云端和 Linux 项目的通用工程方法。

核心工程原则：

```text
不追求单个模块局部最优，而追求整个系统的协同最优。

有依据才实现；
有抽象才扩展；
有测试才交付。

零臆造
零重复造轮子
零无依据特判
零魔法硬编码
零无意义打补丁

高内聚、低耦合、高鲁棒性、热拔插。
```

项目既有目录结构就是一级工程契约。创建或修改文件前，必须先判断文件类型、职责和生命周期，并放入已有正确目录。绝不把 integration test、临时实验、知识文档、数据或脚本随意塞进生产目录。

## 二、必须保留当前交互习惯

用户是编程初学者，优先使用中文解释；专业术语第一次出现时给出准确中文含义，代码中的英文名称保持原样。

工作方式必须是：

```text
一次只推进一个逻辑步骤
→ 读取真实代码/接口
→ 解释当前事实
→ 设计最小变化
→ 先写最小红灯测试
→ 用户执行
→ 等待真实终端输出
→ 定位根因
→ 最小生产修改
→ 用户执行
→ 绿灯
→ 回归测试
→ 下一步
```

没有看到用户的真实测试结果之前，不得假设成功，也不要连续跨越多个未验证步骤。

每次需要修改或新增文件时，优先输出完整 PowerShell 写文件命令：

```powershell
@'

'@ | Set-Content -Encoding UTF8 'C:\dev\Invar\...'
```

并把执行命令紧接在后面，减少用户手工输入。

## 四、必须继承的外部理论、资料和安全边界

当前架构思想明确对齐 Zhiniang Peng 的《A Year of Hacking with LLMs》所强调的研究闭环方向，并吸收已有项目的安全研究方法。对外部资料要遵守：

```text
论文 / 官方文档 / 成熟开源项目 / 既有实现
→ 优先复现与正确转译
→ 再做工程化抽象
```

不要把外部理论、工程推论、假设和实验结果混为一谈。

当前已经沉淀的核心思想：

```text
Deterministic Harness
确定性预处理脚手架

Security Invariant Reasoning
安全不变量推理

In-Silico Verification & Feedback Loop
执行反馈与自适应研究闭环
```

核心研究流程：

```text
Extract
→ Classify
→ Select invariant
→ Form hypothesis
→ Observe
→ Interpret feedback
→ Mutate within policy
→ Re-observe
→ Record evidence
→ Evaluate stop condition
→ Promote only verified claims
```

Agent、Skill、Harness、Evidence、Knowledge 应保持职责分离：

```text
Agent
= 规划、推理、工具选择、分支

Skill
= 工作流顺序、条件、停止条件、安全门禁

Harness
= 确定性工具

Evidence
= 逐轮证据

Knowledge
= 经验证后的事实/知识
```

安全研究历史资料中曾出现真实目标、Token、账户、密码字典、主动 exploit 等内容。绝不把这些作为可复用实现直接迁移。

正确方法：

```text
历史攻击材料
→ 提取算法思想
→ 抽象 operator
→ fixture / mock / localhost
→ TDD
```

默认安全边界：

```text
真实凭据不进入 reusable module
真实目标不写入默认配置
研究 Skill 不携带真实攻击材料
JWT 默认只做安全的结构检查/解析
IDOR / rate-limit / exploit 类 operator 默认使用实验环境
```

## 五、踩过的坑，后续绝对不要再踩

1. 不要没有读取真实接口就凭空设计“大 Agent”。

2. 不要因为 Rust 更快就把 Python 算法全部重写。

3. 不要把 integration test 放进 `src`。

4. 不要没有 `lib.rs` 就直接从 `tests` 导入核心类型。

5. Cargo package `Invar-core` 和 Rust library crate `invar_core` 是两个不同概念。

6. 不要用 lint suppression 代替结构性修复。

7. Python `Optional[T]` 必须在 Rust 中正确映射为 `Option<T>`，不要用空字符串表示 `None`。

8. 不要从日志、文件片段或个人经验猜接口；先读真实源码。

9. 不要为单个测试案例增加特殊 if。

10. 不要为了“完整”复制旧项目中的真实 Token、URL、账号、密码或 exploit。

11. 不要一次修改多个未经验证的逻辑层。

12. 不要在用户还没有反馈测试结果时连续发下一轮修改。

13. 不要重新发明已经存在并被测试验证的逻辑；优先 adapter / bridge，再逐步替换。

14. 不要把 `ResearchCase`、`EvidenceRecord`、`ResearchExecutionResult` 设计成一个巨型对象。
