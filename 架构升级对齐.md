# Cloudflare Security Audit Skill × Invar Architecture Alignment

**Status:** Proposed Architecture Design  
**Date:** 2026-09-18  
**Scope:** Invar Core, Pi orchestration/Skill layer, research state, evidence, findings, multi-run behavior  
**Primary reference:** Cloudflare `security-audit-skill` (main branch, reviewed 2026-09-18)  
**Target repository:** `C:\dev\Invar`

---

## 1. Purpose

This document defines how the strongest architectural ideas in Cloudflare's open-source `security-audit-skill` should be incorporated into Invar without collapsing Invar into a generic LLM security-audit workflow.

The design has one central rule:

> **Pi owns research cognition and orchestration; Invar owns durable state, deterministic execution, evidence, verification contracts, and promotion.**

Cloudflare's project is used as an architectural reference for:

- deterministic coverage accounting;
- focused hunting roles;
- coverage-gap criticism;
- candidate deduplication by fingerprint and root cause;
- adversarial validation;
- machine-readable findings;
- independent final verification;
- additive multi-run history.

Invar retains its own core model:

```text
raw_js
  -> AST
  -> EndpointIR
  -> RiskEngine
  -> HypothesisEngine
  -> AdaptiveSandboxExecutor
  -> InvariantEvaluator
  -> Evidence
  -> Promotion Gate
  -> KnowledgeCard
```

The resulting architecture is a **research system**, not merely an agent prompt.

---

## 2. Executive Architecture Decision

### 2.1 Adopt from Cloudflare

The following concepts become first-class Invar concepts:

1. `CoverageLedger`
2. `ResearchRun`
3. `CandidateFingerprint`
4. `FindingRecord`
5. independent verification before promotion
6. coverage-critic feedback as a first-class orchestration result
7. deterministic schema validation
8. additive multi-run history

### 2.2 Keep in the Pi Skill / Cognitive Layer

The following remain model-facing orchestration roles rather than Invar Core domain objects:

- Hunter
- Coverage Critic
- Adversarial Verifier
- Independent Verifier
- task decomposition
- prompt construction
- agent scheduling
- selection of attack-class methodology

These roles may produce structured outputs, but they do not become the system's source of truth.

### 2.3 Do not copy Cloudflare literally

Invar should **not** copy:

- Cloudflare's agent count or concurrency model;
- Cloudflare's repository-oriented assumptions where they conflict with raw-JS/API analysis;
- a second independent state machine inside the Pi prompt;
- a second findings database outside Invar Core;
- a large collection of model-only rules that cannot be deterministically checked.

The architecture is an adaptation, not a fork of responsibilities.

## 3. Source-Informed Baseline

Cloudflare's current skill runs six phases: reconnaissance, coverage-led hunting, candidate validation, structured output, independent record verification, and target-neutral reporting. It treats coverage as explicit ledger state, consolidates candidates before validation, uses fresh agents to challenge findings, validates structured findings against a schema, and performs another fresh verification pass before reporting. Multiple runs are additive rather than independent resets. [Cloudflare Security Audit Skill](https://github.com/cloudflare/security-audit-skill)

Cloudflare's hunting contract is particularly relevant because it requires every assigned coverage unit to appear exactly once, records reviewed paths and checks, distinguishes `covered`, `candidate`, and `blocked`, and requires candidates to carry a stable fingerprint. The project also reserves a post-wave coverage critic to identify missing units. [HUNTING.md](https://github.com/cloudflare/security-audit-skill/blob/main/skills/security-audit/HUNTING.md)

Cloudflare's validation contract also separates candidate creation from adversarial validation and final record verification. A finding must have a complete source trace, concrete conditions, meaningful impact, and evidence; unresolved factual dependencies remain `needs_validation` rather than being promoted by confidence language. [VALIDATION-AND-REPORTING.md](https://github.com/cloudflare/security-audit-skill/blob/main/skills/security-audit/VALIDATION-AND-REPORTING.md)

Invar already has several compatible foundations: `EndpointIR`, `ResearchCase`, `InvariantEvaluation`, `ResearchExecutionResult`, `Promotion Gate`, and `KnowledgeCard`. Its current project model explicitly states that risk classification is not a confirmed vulnerability and that evidence is the basis for promotion. [Invar handoff and architecture records]

## 4. Architectural Principles

### 4.1 Two planes, one authority

The combined design has two planes:

```text
                           PI / SKILL
                    Cognitive Orchestration Plane

        Understand -> Plan -> Hunt -> Critique -> Verify
                              |
                       Stable Tool Contract
                              |
                              v
                         INVAR CORE
                     Research Authority Plane

      State -> Identity -> Execution -> Evidence -> Decision -> Knowledge
```

The Pi plane may propose and choose actions. The Core plane records what actually exists and what the system is allowed to conclude.

### 4.2 No duplicated truth

There must be one authoritative value for each of these concepts:

- current run state;
- coverage state;
- endpoint identity;
- research task identity;
- evidence identity;
- finding identity;
- promotion state.

A Skill may cache or summarize them, but it must not create a competing authoritative copy.

### 4.3 Evidence outranks narrative

A model statement such as:

> "This endpoint probably lacks authorization."

is a hypothesis.

A structured source trace is source evidence.

A bounded execution result is execution evidence.

A deterministic evaluator result is a decision input.

Only the resulting evidence chain can satisfy the promotion contract.

### 4.4 State is externalized

Long-running progress must not depend on the model remembering what it already did. Coverage, tasks, findings, evidence, and run metadata are durable artifacts owned by Invar.

# 6. Cognitive Layer / Core Boundary

## 6.1 Cognitive Layer

The Cognitive Layer answers:

- What should be researched next?
- Which coverage units should be assigned?
- Which attack class is appropriate?
- What source paths should be followed?
- What is the strongest counterargument to a candidate?
- Which unresolved gap should become a new task?

The Cognitive Layer contains:

```text
Hunter
Coverage Critic
Adversarial Verifier
Independent Verifier
Research Planner
Agent Scheduler
Prompt Builder
```

It may use `pi-subagents` and other Pi capabilities.

## 6.2 Core

The Core answers:

- What endpoint exists?
- What task exists?
- What coverage unit exists?
- What evidence exists?
- What state is authoritative?
- What invariant result was observed?
- What finding record is structurally valid?
- Is promotion permitted?

Core owns:

```text
ResearchRun
CoverageLedger
EndpointIR
RiskEngine
ResearchTask
ResearchCase
Hypothesis
CandidateFingerprint
AdaptiveSandboxExecutor
Evidence
InvariantEvaluator
FindingRecord
PromotionGate
KnowledgeCard
```

## 6.3 Boundary rule

> **Pi may propose Core operations; Pi must not silently create or mutate Core state outside the Tool Contract.**

For example, Pi may say:

```text
"Create coverage unit for authorization on /api/v3/authConf/*"
```

but the authoritative ledger update happens through the Core contract.

# 7. ResearchRun

## 7.1 Purpose

`ResearchRun` represents one bounded execution of Invar against one source state and one research scope.

It is the unit that turns a collection of files and prompts into a reproducible research event.

## 7.2 Proposed model

```text
ResearchRun {
    run_id: string
    repository: string
    target_root: string
    source_ref: SourceRef
    raw_js_hash: string | null
    scope: ResearchScope
    profile: RunProfile
    execution_policy: ExecutionPolicy
    budget: RunBudget | null
    status: RunStatus
    started_at: timestamp
    completed_at: timestamp | null

    coverage_ledger_ref: string
    findings_ref: string
    prior_run_refs: list[string]
}
```

### `SourceRef`

```text
SourceRef {
    vcs: string | null
    commit: string | null
    worktree_dirty: bool
    raw_input_hash: string | null
}
```

The purpose is historical identity, not a requirement that Invar itself must use Git for every input.

## 7.3 Run invariants

1. A run has exactly one authoritative source context.
2. A run cannot claim complete coverage without a complete ledger.
3. A run cannot claim a verified finding without evidence and independent verification.
4. An incomplete run remains available for continuation and later reconciliation.
5. A prior run never automatically becomes current evidence merely because its source reference looks similar.

# 8. CoverageLedger

## 8.1 Why it is needed

`EndpointIR` says what exists.

`CoverageLedger` says what the research process has committed to examine.

Without the ledger, the statement:

> "We audited the API."

has no machine-verifiable meaning.

## 8.2 Coverage unit

A coverage unit is the smallest deterministic research obligation that can be assigned, completed, blocked, or reconsidered.

Proposed shape:

```text
CoverageUnit {
    coverage_id: string
    surface: string
    boundary: string
    subsystem: string
    attack_class: string
    starting_paths: list[string]

    status: planned | in_progress | covered | candidate | blocked |
            deferred | out_of_scope

    owner_agent_id: string | null
    reviewed_paths: list[string]
    check_refs: list[string]
    candidate_fingerprints: list[string]
    unresolved: list[UnresolvedFact]
    prior_refs: list[string]
}
```

## 8.3 Example

```json
{
  "coverage_id": "api-authconf-authorization",
  "surface": "api",
  "boundary": "authenticated-user-to-privileged-config",
  "subsystem": "authConf",
  "attack_class": "authorization",
  "starting_paths": [
    "api/v3/authConf/saveAuth"
  ],
  "status": "planned",
  "owner_agent_id": null,
  "reviewed_paths": [],
  "check_refs": [],
  "candidate_fingerprints": [],
  "unresolved": [],
  "prior_refs": []
}
```

## 8.4 Coverage states

### `planned`
The work exists but has not begun.

### `in_progress`
An owner has been assigned and is actively working it.

### `covered`
The unit was examined with sufficient checks and has no unresolved fact relevant to its coverage obligation.

### `candidate`
The unit produced one or more surviving candidate fingerprints.

### `blocked`
A meaningful portion was inspected, but a required fact or capability prevents completion.

### `deferred`
The unit was intentionally not executed in this run because of budget, profile, or explicit scheduling policy.

### `out_of_scope`
The unit is known but excluded from the current scope. It must never be counted as covered.

## 8.5 Coverage invariants

- Every assigned coverage ID appears exactly once in the ledger.
- A covered unit has an owner, reviewed paths, and checks.
- A candidate unit has linked fingerprints.
- A blocked unit has unresolved facts but no promoted finding.
- Out-of-scope units do not contribute to coverage percentage.
- The parent process is the sole writer of the shared ledger.

## 8.6 Coverage percentage

Coverage percentage must be computed from explicit ledger units, not from the model's prose.

A future implementation may support:

```text
coverage_percentage = covered_weight / total_in_scope_weight
```

where weights are deterministic and stored in the ledger. The first implementation may use a simple count if weighting is not yet justified.

# 9. Hunter

## 9.1 Role

A Hunter investigates assigned coverage units using source-grounded reasoning and bounded local execution where allowed.

The Hunter is **not** a global auditor.

The Hunter must have:

- assigned coverage IDs;
- subsystem and trust-boundary context;
- starting paths;
- selected attack methodology;
- explicit excluded work;
- a structured result contract.

## 9.2 Output boundary

Hunters may return:

```text
covered
candidate
blocked
uncovered
hardening
```

They do not directly edit the authoritative ledger or findings store.

## 9.3 Invar adaptation

The Hunter's structured result should map into:

```text
CoverageUnit updates
Candidate proposals
Uncovered-unit proposals
```

The Parent then commits those changes through Core.

# 10. Coverage Critic

## 10.1 Role

Coverage Critic answers one question:

> **"What important research space did the previous wave fail to cover?"**

It must not simply repeat the Hunter's job.

## 10.2 Inputs

The critic receives:

- architecture/context artifact;
- current `CoverageLedger`;
- current candidate fingerprints;
- prior-run gap summary;
- source reference;
- current scope.

## 10.3 Output

```text
MissingCoverageUnit {
    surface
    boundary
    subsystem
    attack_class
    starting_paths
    reason
}
```

The Parent converts approved missing units into new `planned` Core ledger entries.

## 10.4 Critical distinction

```text
Hunter:
    "I found / did not find a problem."

Coverage Critic:
    "This region / boundary / attack class still has an unfulfilled obligation."
```

## 11.1 Candidate is not a finding

A candidate is a source-grounded security hypothesis that survived initial plausibility checks but has not passed all verification gates.

```text
Risk
  !=
Hypothesis
  !=
Candidate
  !=
Finding
  !=
Knowledge
```

## 11.2 Candidate fields

```text
    conditions: list[Condition]

}
```

# 12. CandidateFingerprint

## 12.1 Purpose

Fingerprint gives the same underlying root cause a stable identity across:

- multiple Hunters;
- multiple endpoints;
- multiple runs;
- candidate states;
- validation passes.

## 12.2 Requirements

A fingerprint:

- must be deterministic;
- must represent the root cause rather than a line number;
- must not encode agent ID;
- must not encode severity;
- must not encode verdict;
- must not change merely because the candidate moved from `candidate` to `verified`.

Cloudflare uses the same source-derived fingerprint across states and explicitly prevents line, wave, agent, severity, or verdict from becoming part of the fingerprint. [HUNTING.md](https://github.com/cloudflare/security-audit-skill/blob/main/skills/security-audit/HUNTING.md)

## 12.3 Proposed form

```text
CandidateFingerprint {
    value: string
    algorithm: string
    canonical_factors: object
}
```

The first implementation should preserve the canonical factors that generated the fingerprint so that a future schema change can be diagnosed rather than silently creating identity drift.

## 12.4 Example

```text
root cause:
missing resource-ownership enforcement

canonical factors:
- attack_class = authorization
- boundary = resource ownership
- sink component = user-resource mutation service
- missing control = owner check

fingerprint:
authz:/user-resource/missing-owner-check
```

The exact algorithm is intentionally not hard-coded in this document; it must be specified in an implementation ADR together with determinism and backward-compatibility tests.

# 13. Adversarial Verifier

## 13.1 Purpose

The Adversarial Verifier is intentionally biased toward disproving a candidate.

This directly adopts Cloudflare's principle that the agent which finds a candidate should not be the same agent that validates it. [VALIDATION-AND-REPORTING.md](https://github.com/cloudflare/security-audit-skill/blob/main/skills/security-audit/VALIDATION-AND-REPORTING.md)

## 13.2 Verification questions

Every candidate must be challenged on:

1. **Trace:** Does the claimed data/control flow actually exist?
2. **Exploitability:** Can the claimed condition be realized?
3. **Impact:** Is there a real affected principal, resource, or security outcome?
4. **Mitigation:** Does another layer prevent exploitation?
5. **Baseline:** Does an equivalent pattern behave differently for a justified reason?
6. **Runtime/parser behavior:** If the claim depends on runtime semantics, has that behavior been established rather than inferred?
7. **Scope:** Is the result actually inside the current research boundary?

## 13.3 Outputs

```text
VERIFIED
CORRECTED
REJECTED
INCONCLUSIVE
```

`INCONCLUSIVE` is required when a decisive fact is outside the available evidence boundary.

## 13.4 Layer separation

Adversarial verification is a **cognitive challenge**.

`InvariantEvaluator` remains the deterministic decision mechanism over collected evidence.

Therefore:

```text
Adversarial Verifier
    ↓
"Can I disprove this?"

InvariantEvaluator
    ↓
"What did the observed evidence establish?"
```

Neither replaces the other.

# 14. FindingRecord

## 14.1 Why it is needed

Invar currently has `KnowledgeCard`, which is the promoted knowledge layer. A richer intermediate object is required between evidence/evaluation and long-term knowledge.

The proposed chain is:

```text
Candidate
  ↓
Evidence
  ↓
InvariantEvaluation
  ↓
FindingRecord
  ↓
Independent Verification
  ↓
Promotion Gate
  ↓
KnowledgeCard
```

## 14.2 Proposed model

```text
FindingRecord {
    finding_id: string
    verdict: confirmed | rejected | needs_validation

    fingerprint: string | null
    title: string
    description: string

    root_cause: string | null
    claimed_root_cause: string | null
    intended_behavior: string | null

    trace: list[TraceStep]
    conditions: list[Condition]
    execution: ExecutionRecord | null

    endpoint_refs: list[string]
    coverage_refs: list[string]
    hypothesis_refs: list[string]
    evidence_refs: list[string]

    severity: Severity | null
    confidence: Confidence
    remediation: Remediation | null

    verification: VerificationSummary
    provenance: Provenance
}
```

## 14.3 Verdict contract

### `confirmed`
Requires:

- complete source trace;
- evidence for the claimed root cause;
- bounded observed or otherwise authoritative result;
- meaningful security impact;
- complete conditions;
- no visible preventing layer;
- passing independent verification.

### `needs_validation`
Requires:

- a precise source-grounded lead;
- an exact unresolved blocker;
- a safe validation plan;
- no severity;
- no false claim of completion.

### `rejected`
Requires:

- an explicit reason describing the incorrect claim or preventing control.

These semantics align with Cloudflare's current structured output contract, while keeping Invar's own `InvariantEvaluation` states intact. [report-schema.json](https://github.com/cloudflare/security-audit-skill/blob/main/skills/security-audit/report-schema.json)

# 15. Finding Schema

## 15.1 Schema as executable contract

A machine-readable schema must become the authoritative structural contract for `FindingRecord` serialization.

The schema must enforce:

- required fields;
- allowed enums;
- trace structure;
- field types;
- `additionalProperties: false` for strict records;
- separation of confirmed versus unresolved forms.

Cloudflare's current schema does exactly this for its `findings.json`, and its validator explicitly treats structural validity as distinct from factual correctness. [report-schema.json](https://github.com/cloudflare/security-audit-skill/blob/main/skills/security-audit/report-schema.json)

## 15.2 Structural versus factual validation

```text
Schema Validator
    ↓
"Is the record structurally valid?"

Independent Verifier
    ↓
"Are the record's factual claims actually true?"
```

Both are required.

## 15.3 Trace contract

The trace must be:

```text
entrypoint
  ↓
propagation
  ↓
...
  ↓
sink
```

Each step requires:

- repository-relative file path;
- source line;
- function/method scope;
- factual description.

No absolute host paths should appear in portable finding records.

# 16. Independent Verification

## 16.1 Position in the pipeline

The independent verifier is the final factual cross-check before promotion.

```text
Candidate
    ↓
Adversarial Validation
    ↓
FindingRecord
    ↓
Schema Validation
    ↓
Independent Verification
    ↓
Promotion Gate
```

## 16.2 Independence rule

The verifier must be a fresh execution context that did not originate the finding.

It must independently inspect:

- source trace;
- root cause;
- intended behavior;
- conditions;
- evidence references;
- execution summary;
- remediation relevance;
- severity/confidence justification.

## 16.3 Verification results

```text
VERIFIED
CORRECTED
REJECTED
```

`CORRECTED` requires a specific field-level correction and another schema validation pass. `REJECTED` prevents promotion.

## 16.4 Invar responsibility

Invar Core must store the independent verification result and use it as a required input to `PromotionGate`.

Pi owns the verifier role; Core owns the resulting fact.

# 17. ResearchTask Contract

## 17.1 Existing problem

The current public Rust `ResearchTask` is intentionally thin:

```rust
ResearchTask {
    task_id: String,
    method: String,
    path: String,
}
```

The current Python adapter reconstructs an `EndpointIR` with only `method` and `path`, which causes `source_file`, `extracted_params`, `tags`, `risk_score`, `confidence`, and other endpoint metadata to be lost. This has already been experimentally confirmed in the project audit log.

The important architectural lesson is not "copy more fields into `ResearchTask`."

The lesson is:

> **ResearchTask must reference research context without duplicating the entire EndpointIR object.**

## 17.2 Proposed contract

```rust
ResearchTask {
    task_id: String,
    endpoint_id: String,
    coverage_id: String,
    hypothesis_id: Option<String>,
    profile: String,
}
```

Compatibility fields may be retained during migration where required by the current IPC surface:

```text
method
path
```

but they should become projections of the canonical endpoint identity rather than independent truth.

## 17.3 Resolution model

```text
ResearchTask
   │
   │ endpoint_id
   ▼
EndpointRegistry / EndpointIR
   │
   ├── source_file
   ├── line
   ├── extracted_params
   ├── tags
   ├── risk_score
   ├── confidence
   └── call_signature
```

Then:

```text
ResearchTask
   + EndpointIR
   + CoverageUnit
   + Hypothesis
   ↓
ResearchCase
```

## 17.4 Required invariants

1. A task must resolve to exactly one endpoint identity.
2. Endpoint context must not be silently reconstructed with defaults when the canonical endpoint exists.
3. A missing endpoint reference is a contract error, not a reason to silently create a thin endpoint.
4. Provenance must remain recoverable from task to endpoint to raw input.
5. A task may contain execution profile information without owning the endpoint's static metadata.


- stable IDs;
- artifact references when applicable;
- concise human-readable summary;
- structured evidence fields where required.

The model must never infer a successful state merely because a process exited without an exception.

# 19. State Transitions

## 19.1 Run state machine

```text
INIT
  ↓
SCOPE_VERIFIED
  ↓
CONTEXT_READY
  ↓
PLAN_READY
  ↓
EXECUTING
  ↓
EVIDENCE_COLLECTED
  ↓
EVALUATED
  ├── VERIFIED
  ├── REFUTED
  └── INCONCLUSIVE
  ↓
REPORT_READY
```

Any required step may transition to:

```text
BLOCKED
```

An incomplete run must not be represented as `REPORT_READY`.

## 19.2 Coverage state machine

```text
planned
   ↓
in_progress
   ├── covered
   ├── candidate
   └── blocked

planned
   └── deferred

known/excluded
   └── out_of_scope
```

## 19.3 Candidate state machine

```text
proposed
   ↓
validating
   ├── rejected
   ├── inconclusive
   └── supported
          ↓
     FindingRecord
```

## 19.4 Finding state machine

```text
candidate
  ↓
validated
  ↓
schema_valid
  ↓
independently_verified
  ├── VERIFIED → PromotionGate
  ├── CORRECTED → schema_valid → independent verification
  └── REJECTED
```

## 19.5 Promotion rule

Promotion is allowed only when all required predicates are true:

```text
source trace complete
AND
required evidence present
AND
invariant evaluation resolved
AND
impact demonstrated
AND
independent verification passed
AND
schema valid
AND
run/source context valid
AND
no unresolved blocker
```

# 20. Multi-Run Behavior

## 20.1 Core principle

A new run is additive, not a reset.

Prior work may contribute evidence, priority, and known gaps, but prior status is not blindly trusted.

Cloudflare's current skill explicitly reads compatible prior ledgers and findings, revalidates changed source, carries forward only appropriate same-source confirmed records, and keeps unresolved or deferred work visible. [SKILL.md](https://github.com/cloudflare/security-audit-skill/blob/main/skills/security-audit/SKILL.md)

## 20.2 Prior confirmed finding

If:

```text
source context unchanged
AND
relevant conditions unchanged
AND
current evidence contract still satisfied
```

then the prior fingerprint may seed the current run.

It must still pass the current independent verification path.

## 20.3 Prior finding with changed source

If relevant source changed:

```text
prior confirmed
     ↓
current planned revalidation unit
     ↓
current evidence
```

The old record does not suppress current research.

## 20.4 Prior `needs_validation`

Always remains visible as unresolved work.

It may seed a current planned unit, but it never suppresses the current unit and never gains severity merely by age.

## 20.5 Prior `rejected`

Suppress only the exact unchanged failed claim.

Do not suppress the entire coverage unit.

A changed source, changed boundary, or changed evidence may reopen the research space.

## 20.6 Multi-run objective

Each new run should preferentially allocate effort to:

1. changed source;
2. prior unresolved gaps;
3. unreviewed boundaries;
4. uncovered attack classes;
5. revalidation targets;
6. only then broad same-source re-passes.

# 22. Reporting Model

Reporting should be a projection of Core state, not a second source of truth.

Recommended outputs:

```text
REPORT.md
FINDINGS-DETAIL.md
NEEDS-VALIDATION.md
coverage-summary.md
findings.json
```

The report generator must derive facts from:

```text
FindingRecord
CoverageLedger
ResearchRun
Evidence summaries
```

A report must never contain a finding that does not exist in the machine-readable finding set.

Likewise, a finding record must never contain a claim that the report silently omits when the omission changes meaning.

# 23. Security and Execution Boundaries

This design retains Invar's existing authorization boundary:

```text
Asset discovery
   !=
Testing authorization
```

Stage 0 establishes scope before any active testing.

Cloudflare's source-first skill similarly keeps source inspection separate from live or shared-environment testing and requires bounded local execution where code execution is needed. [SKILL.md](https://github.com/cloudflare/security-audit-skill/blob/main/skills/security-audit/SKILL.md)

Invar-specific requirement:

```text
Static analysis may proceed without dynamic authorization.
Dynamic execution requires explicit authorization and an execution policy.
```

The research executor must remain responsible for:

- request bounds;
- mutation policy;
- sandbox limits;
- evidence capture;
- stop conditions.

Pi must not bypass the executor with ad-hoc `curl`, shell probes, or manual request substitution during the formal research loop.

# 24. Explicitly Prohibited Designs

## 24.1 No second Invar inside Pi

Do not implement:

```text
PiRiskEngine
PiHypothesisEngine
PiPromotionGate
```

that duplicate Core semantics.

## 24.2 No checklist-as-vulnerability design

Never map:

```text
missing best practice
```

to:

```text
confirmed vulnerability
```

A concrete affected boundary, resource, or security outcome is required.

## 24.3 No severity on unresolved records

`needs_validation` must not receive a severity merely to make reports sortable.

## 24.4 No hidden coverage

Do not allow:

```text
"Agent says the API was checked"
```

to count as coverage.

Coverage must be represented by ledger units and checks.

## 24.5 No self-verification as final proof

The agent that generated a candidate cannot be the only validator for that candidate.

## 24.6 No copy-all-fields ResearchTask

Do not solve the current adapter defect by dumping the entire `EndpointIR` into `ResearchTask`.

Instead, use stable references such as:

```text
endpoint_id
coverage_id
hypothesis_id
```

and resolve canonical context from Core.

## 24.7 No model-only persistence

Do not rely on chat memory for:

- coverage state;
- candidate history;
- source identity;
- evidence identity;
- run status;
- promotion status.

## 24.8 No artifact-path guessing

Do not reconstruct session/artifact paths from model assumptions.

Use tool-returned artifact references or Core-managed IDs.

Never use unbounded filesystem discovery such as `find /` as an error-recovery mechanism.

## 24.9 No automatic promotion on HTTP 200

An observed `2xx` response is an input to evaluation, not a vulnerability verdict.

## 24.10 No risk-to-vulnerability shortcut

```text
CRITICAL / HIGH risk
    !=
confirmed vulnerability
```

## 24.11 No blind prior-run trust

A prior `confirmed` record must not be considered current merely because its path or commit string appears similar.

## 24.12 No coverage reduction by budget without disclosure

If budget prevents planned units from being executed, mark them `deferred` with a reason. Never silently shrink the coverage claim.

## 24.13 No report-first workflow

Do not write the final report before machine-readable findings and independent verification have completed.

## 24.14 No hardcoded target-specific logic

Do not add:

```text
if endpoint == "..."
if test_case_001
if target_url == "..."
```

for a single observed sample.

Generalize through contracts, profiles, schemas, and reusable research strategies.

# 25. Migration Order

The migration must proceed in dependency order, not by adding a collection of disconnected classes.

## Phase M0 — Architecture freeze

1. Accept this document as the design baseline.
2. Record ADRs for each new Core concept.
3. Freeze terminology:
   - Coverage Unit
   - Research Run
   - Candidate
   - Fingerprint
   - FindingRecord
   - Independent Verification
4. Do not implement parallel models under different names.

## Phase M1 — ResearchTask contract repair

Fix the currently confirmed contract seam first.

Goal:

```text
ResearchTask
   ↓ endpoint_id
canonical EndpointIR
```

Add contract tests that prove:

- provenance survives;
- extracted parameters survive through canonical resolution;
- tags/risk are not silently reset;
- missing references fail explicitly.

Do not add Cloudflare features before this seam is stable.

## Phase M2 — ResearchRun

Add:

```text
run_id
source_ref
scope
profile
budget
status
```

Make run identity available through Tool Contract.

## Phase M3 — CoverageLedger

Implement:

- CoverageUnit model;
- ledger serialization;
- deterministic IDs;
- parent-only write policy;
- state transition validation;
- coverage validator.

Integrate Stage 1 output into initial ledger generation.

## Phase M4 — CandidateFingerprint

Implement:

- canonical factors;
- deterministic fingerprint generation;
- duplicate consolidation;
- multi-run identity preservation;
- tests for unrelated-root-cause separation.

## Phase M5 — FindingRecord + schema validation

Implement:

- strict JSON schema;
- serialization/deserialization;
- schema validator;
- candidate-to-finding transformation.

Keep `KnowledgeCard` unchanged initially; adapt only its input boundary.

## Phase M6 — Independent Verification

Add:

```text
FindingRecord
  ↓
IndependentVerifier
  ↓
VerificationResult
```

Make the result mandatory for promotion.

## Phase M7 — Coverage Critic / Hunter Skill integration

Update Pi Skill so that:

```text
CoverageLedger
→ Hunter wave
→ Coverage Critic
→ ledger update
```

becomes the standard orchestration loop.

## Phase M8 — Multi-run continuity

Add prior-run ingestion, source-change detection, fingerprint carry-forward, and unresolved-gap resurfacing.

## Phase M9 — Reporting integration

Generate all human-readable reports from Core records.

Every migration phase requires both unit-level and integration-level verification.

## 26.1 Core contract tests

- coverage claims for `out_of_scope` units;
- invented absolute source paths;

```text

→ Coverage
→ ResearchTask
→ Hypothesis
→ ResearchCase
→ Evidence
→ Evaluation
→ FindingRecord
→ Independent Verification
```

This test is a **software correctness test**, not a substitute for real authorized target validation.

The existing Invar project already distinguishes software-layer TDD from real-target evidence, and that distinction must remain intact.

# 27. Recommended Pi Skill Operating Loop

The Pi Skill should eventually use this compact controller loop:

```text
1. Inspect current ResearchRun
2. Check scope and source identity
3. Read current CoverageLedger
4. Determine next planned units
5. Launch focused Hunter(s)
6. Commit structured results through Core
7. Run Coverage Critic
8. Commit newly identified gap units
9. Consolidate candidate fingerprints
10. Launch Adversarial Verifier(s)
11. Record Evidence and InvariantEvaluation
12. Materialize FindingRecord(s)
13. Run schema validation
14. Launch Independent Verifier(s)
15. Apply corrections/rejections
16. Run Promotion Gate
17. Promote only eligible findings
18. Update KnowledgeCard
19. Produce report projections
20. Mark run COMPLETE or INCOMPLETE with exact reason
```

The controller must not invent a second data model. It reads and mutates Core state through stable contracts.

# 29. Definition of Done for the Alignment

The architecture alignment is complete only when all of the following are true:

### Core

- `ResearchRun` has a stable contract.
- `CoverageLedger` is authoritative for coverage.
- `CandidateFingerprint` is deterministic and persistent.
- `FindingRecord` is schema-validated.
- independent verification is represented in Core state.
- `PromotionGate` requires independent verification.
- `KnowledgeCard` is downstream of verified findings.

### Contracts

- `ResearchTask` references canonical endpoint context.
- provenance survives all transitions.
- no silent thin-endpoint reconstruction occurs.
- Tool Contracts expose stable IDs and machine-readable states.

### Cognitive Layer

- Hunter operates on assigned coverage units.
- Coverage Critic identifies missing coverage rather than repeating hunting.
- Adversarial Verifier is separate from the finding generator.
- Independent Verifier is a fresh verification role.

### Multi-run

- prior runs are additive;
- changed-source revalidation is explicit;
- unresolved work remains visible;
- fingerprints remain stable across runs.

### Reporting

- reports are projections of Core state;
- machine-readable and prose outputs cannot silently disagree;
- incomplete runs disclose exact gaps.

# 31. Architectural Thesis

The most important lesson from Cloudflare's project is not a particular prompt or agent count.

It is the decision to make **coverage, candidate identity, validation, structured findings, and independent verification explicit system objects** rather than leaving them inside model conversation.

That principle fits Invar exceptionally well.

Invar's existing architecture already separates:

```text
Risk
Hypothesis
Evidence
Invariant
Promotion
Knowledge
```

The Cloudflare alignment adds the missing research-governance layer:

```text
Run
Coverage
Candidate Identity
Finding
Independent Verification
```

The resulting system is therefore:

```text
                  WHAT EXISTS
                      │
                   EndpointIR
                      │
                      ▼
                  WHAT TO STUDY
                      │
                 CoverageLedger
                      │
                      ▼
                 WHAT TO TRY
                      │
                ResearchTask
                      │
                      ▼
                 WHAT WE THINK
                      │
                  Hypothesis
                      │
                      ▼
                 WHAT HAPPENED
                      │
                    Evidence
                      │
                      ▼
                WHAT IT MEANS
                      │
             InvariantEvaluator
                      │
                      ▼
               WHAT SURVIVED
                      │
                FindingRecord
                      │
                      ▼
                WHO CHECKED IT
                      │
           Independent Verification
                      │
                      ▼
                WHAT IS ALLOWED
                      │
                Promotion Gate
                      │
                      ▼
                WHAT WE KNOW
                      │
                KnowledgeCard
```

This is the target architecture for the next Invar implementation phase.
