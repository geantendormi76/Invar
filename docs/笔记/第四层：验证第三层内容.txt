# Authorization Knowledge Validation Plan

## Claude-Red IDOR × A.I.G Authorization × Invar

## 0. 当前阶段

当前不进入实现。

当前目标：

> 验证“外部成熟授权研究机制”是否真的能够改善 Invar 的研究确定性，而不是因为外部方案看起来复杂就默认吸收。

当前 Invar 已经具备：

```text id="q9m1a4"
ResearchTask
    ↓
ResearchCase
    ↓
ProbeAttempt
    ↓
EvidenceRecord
    ↓
Invariant / Verification
```

其中 `ResearchTask` 已包含 `task_id / endpoint_id / coverage_id / hypothesis_id / profile / method / path`；`ResearchCase` 保存 hypotheses、attempts、decision；`ProbeAttempt` 保存每轮实验及 mutation 信息；`EvidenceRecord` 保存请求、响应及证据元数据。

所以本阶段原则是：

> **优先验证现有骨架能否承载外部成熟方法，而不是先扩展骨架。**

---

# 1. 四个需要验证的核心缺口

前一阶段的知识归一化已经把问题压缩成四项：

```text id="h4m7te"
GAP-01
Object Reference

GAP-02
Authorization Baseline

GAP-03
Differential Variable

GAP-04
Knowledge Provenance
```

其中前三个属于“授权研究本身”的核心机制。

第四个属于“长期工程吸收”的基础设施。

---

# 2. 验证优先级

当前不做四个实验并行推进。

顺序固定为：

```text id="2h6yqh"
EXP-01
Object Reference
        ↓
EXP-02
Authorization Baseline
        ↓
EXP-03
Differential Variable
        ↓
EXP-04
Knowledge Provenance
```

原因不是“重要性排名”，而是依赖关系：

```text id="2k1jpm"
没有明确对象
    ↓
无法定义授权关系

没有授权基线
    ↓
无法判断差分

没有差分变量
    ↓
无法证明变异导致结果变化

前三项没有成立
    ↓
Provenance 只是在记录错误知识
```

因此 **EXP-01 是唯一需要最先做的实验。**

---

# 3. EXP-01：Object Reference Validation

## Hypothesis

> 如果把传统“参数名启发式 IDOR”提升为“对象引用语义”，Invar 能更稳定地识别授权研究真正需要比较的对象，而不会把所有 `id` 参数都误认为 IDOR。

Claude-Red 的材料真正有价值的地方就在这里：它并不把 IDOR 定义为“参数名叫 id”，而是关注客户端能够控制、并且可能指向受保护资源的对象引用。其 Web Skill 目录也明确把 IDOR 作为独立攻击面。

---

## Baseline

当前候选识别主要依赖：

```text id="z7bfzq"
id
user_id
account_id
tenant_id
...
```

这属于：

> **Candidate Heuristic**

而不是完整 Object Reference Model。

因此实验基线定义为：

```text id="k6h3bn"
Input
↓
参数关键词
↓
IDOR candidate
```

---

## Variable

只改变一个东西：

> **对象引用的识别方式。**

不改变：

```text id="2p1br4"
Sandbox
Transport
Evidence
Verification
ResearchTask
```

---

## 测试样本

至少构造以下 6 种对象引用：

```text id="g9h0fr"
1. /users/{id}

2. {"user_id": "..."}

3. {"resource": {"owner": "..."}}

4. Header / Cookie 中的对象引用

5. JWT claim 中的主体 / 租户引用

6. 不含 id 字样，但语义上指向资源的字段
```

注意：

这不是要攻击目标。

而是构造一个**对象引用分类问题**：

```text “这个值究竟是不是一个资源引用？”
```

---

## Metrics

统计：

```text id="ksd0ri"
Reference Recognition
对象引用识别数量

False Candidate
错误识别数量

Missed Reference
漏识别数量

Normalization Consistency
不同表示是否能归一化到同一对象语义
```

---

## Expected Result

如果机制成立：

```text id="a7m7wq"
不同传输位置
+
不同字段名
+
不同编码
        ↓
统一进入 Object Reference 语义
```

---

## Falsification Condition

出现以下任一情况：

```text id="e9p6u4"
1. 语义抽象没有比关键词启发式增加信息

2. 误报明显增加

3. 相同资源的不同表达无法稳定归一化

4. Object Reference 模型无法指导后续授权实验
```

那么：

> **暂不引入独立 Object Reference Contract。**

---

# 4. EXP-02：Authorization Baseline Validation

## Hypothesis

> 如果把“正常授权行为”定义为显式基线，Invar 就能够区分“请求成功”与“授权关系被违反”。

这是 Claude-Red 与 A.I.G 都隐含/明确要求的核心步骤。

Claude-Red 的 IDOR 流程要求先建立正常用户行为，再进行跨用户对象引用替换；A.I.G 当前研究方法同样要求先理解能力、边界和预期防御，再进行最小验证。

---

## Baseline

先定义：

```text id="m8y2pj"
Principal A
+
Object A
+
Action X
```

得到：

```text Allowed
```

再定义：

```text
Principal A
+
Object B
+
Action X
```

得到：

```text Expected Denied
```

---

## Variable

唯一变量：

```text id="b4d5hn"
Object ownership / authorization relation
```

不改变：

```text method
path
headers
body structure
transport
```

---

## Metrics

记录：

```text id="4l4p7k"
baseline_status
cross_subject_status
business_semantics
evidence_difference
authorization_difference
```

---

## Expected Result

最终应该能得到类似：

```text id="c86xqk"
A → A → allowed
A → B → denied
```

而不是：

```text
200 → safe
403 → safe
```

---

## Falsification Condition

如果同一实验里：

```text id="6i0r4z"
HTTP 结果变化
但无法判断授权关系是否变化
```

说明：

> Invar 需要进一步强化 Authorization Baseline 语义层。

---

# 5. EXP-03：Differential Variable Validation

## Hypothesis

> A.I.G 的“每轮只改变一个变量”思想，可以减少授权研究过程中的因果歧义，并且能够直接复用 Invar 现有 ProbeAttempt 记录链。

A.I.G 当前 Agent Red Team 方法把 hypothesis、action、response、verdict、defense signal、next decision 组织成连续实验过程；这与 Invar 已有 `ProbeAttempt` / `mutation_reason` 的结构存在明显同构。

---

## Baseline

首先固定：

```text id="w5cb7g"
Principal
Object
Method
Path
Headers
Body
```

---

## Variable

每轮只改变：

```text id="6lrd1h"
Round 1:
Principal

Round 2:
Object Reference

Round 3:
Method

Round 4:
Context / Role
```

不要同时改变两个。

---

## 核心验证

需要证明：

```text id="v2x3wp"
一次变化
↓
一个可观察差异
↓
能够解释差异原因
```

---

## Metrics

```text id="q2y2ls"
Variables Changed Per Attempt

Cause Attribution

Repeated Attempts

Evidence Reuse

Mutation Justification Completeness
```

---

## Expected Result

如果成立：

```text id="g5s5xq"
attempt 1
baseline

attempt 2
+ object mutation

attempt 3
+ role mutation
```

每一步的差异都可以追溯。

---

## Falsification Condition

出现：

```text id="w7ic9o"
单轮同时变化多个变量
或
无法从 Evidence 判断是哪一个变化造成结果
或
mutation_reason 无法解释实验因果
```

那么当前 Invar 的 mutation contract 还不够强。

---

# 6. EXP-04：Knowledge Provenance Validation

## Hypothesis

> 如果每一个外部吸收的安全机制都携带源项目、源文件、版本和本地适配记录，那么未来升级 Skill 时，可以判断哪些内容是外部事实，哪些是 Invar 自己的修改。

这一步尤其必要，因为 A.I.G 自身目前仍处于快速演化阶段：v4.6.0 对 `aig-agent-redteam` 做过 mutation engine refactor，v4.6.2 又加入 benchmark 和 false-positive 修复，v4.6.3 继续新增测试与文档变化。

---

## 需要记录的最小信息

```text id="8ucf8o"
source_project
source_repository
source_file
source_revision
source_section
source_mechanism
local_adaptation
validation_status
```

例如：

```text
source_project:
Claude-Red

source_file:
Skills/web/offensive-idor/SKILL.md

source_mechanism:
object-reference based authorization differential

local_adaptation:
Invar deterministic HTTP verification

validation_status:
experimental
```

---

## Variable

唯一变化：

> 是否带完整 Provenance。

其他内容完全相同。

---

## Expected Result

以后看到一个研究规则时，可以回答：

```text id="8xgj4p"
它从哪里来的？
哪个版本？
我们改过什么？
验证过没有？
```

---

## Falsification Condition

如果 Provenance：

```text id="m6bq8e"
无法区分源知识和本地规则
或
升级外部知识后无法追踪影响
```

则说明 Provenance 设计还不够。

# 8. 为什么 EXP-01 必须第一个做

这是整个规划里最重要的判断。

如果：

```text id="n8l8pd"
对象是什么？
```

这个问题没有解决，那么：

```text id="x1a4yd"
授权关系
```

就无法定义。

没有授权关系：

```text id="nbi9p8"
baseline
```

就无法定义。

没有 baseline：

```text id="n9o3c9"
difference
```

就无法定义。

没有 difference：

```text id="jv5j01"
mutation
```

就只是 payload throwing。

所以真正的链条是：

```text id="f41cjp"
Object
↓
Authorization Relation
↓
Baseline
↓
Differential Variable
↓
Mutation
↓
Evidence
```

# 9. 与 Invar 当前契约的映射

现在不修改任何类型，只做概念映射：

| 验证机制                   | 现有 Invar 载体                            | 当前状态          |
| ---------------------- | -------------------------------------- | ------------- |
| Preconditions          | `ResearchScope`                        | 已有            |
| Attacker               | `ThreatModel / AttackerProfile`        | 已有            |
| Asset                  | `ThreatModel.assets`                   | 基础已有          |
| Subject                | `AttackerProfile`                      | 已有            |
| Object Reference       | Triage heuristic / EndpointIR          | **不足**        |
| Authorization Relation | Invariant / Hypothesis                 | 基础已有          |
| Baseline               | Evidence / ResearchCase                | **需要实验确认**    |
| Differential Variable  | `ProbeAttempt.mutation_reason`         | **需要实验确认**    |
| Mutation Family        | mutation policy                        | 部分已有          |
| Observation            | EvidenceRecord / DenialModel           | **较成熟**       |
| Evidence               | EvidenceRecord                         | **成熟**        |
| Verdict                | ResearchDecision / Verification        | **成熟但需要语义映射** |
| Escalation             | research loop / mutation policy        | 部分已有          |
| Stop Condition         | budget / max rounds                    | 已有            |
| Inconclusive           | ResearchResult                         | 已有            |
| Provenance             | metadata / refs                        | **需要统一**      |
| Reproducibility        | ResearchCase / ProbeAttempt / Evidence | **基础成熟**      |

这也是为什么我现在仍然不建议先改 `ResearchTask`。当前 `ResearchTask` 已经承担的是执行任务身份，而不是完整授权语义。

# 10. 重要的外部证据反馈

这里有一个特别值得加入我们工程思维的事实：

A.I.G 最近连续版本实际上一直在修：

```text
evidence-free false positives
tool-call stalls
incomplete scans
```

并且 v4.6.3 又增加了：

```text
finished test cases written to disk
```

以及 API Checker 的 fingerprint reliability 改进。

这说明：

> **“研究过程可记录、可重放、可验证”并不是锦上添花，而是成熟系统后期必然遇到的核心问题。**

所以我们现在把验证设计放在代码之前，是对的。

# 11. 当前阶段不做什么

在 EXP-01 前冻结：

```text id="7gvzyt"
❌ 不创建 SKILL.md
❌ 不扩展 ResearchTask
❌ 不新增 ObjectReference 类
❌ 不新增 MutationFamily 枚举
❌ 不改变 DenialModel
❌ 不调整 VerificationGate
❌ 不复制 A.I.G Agent Runtime
❌ 不复制 Claude-Red Skill Corpus
```

原因很简单：

> 现在我们要验证“缺口到底是不是真的缺口”。

而不是：

> 先假设缺口存在，然后围绕假设建一堆代码。

# 12. EXP-01 的最小实验环境

为了严格控制变量，EXP-01 不应该一上来依赖真实目标。

需要一个非常小的抽象测试样本：

```text id="v8z5hy"
Endpoint A
    /users/{user_id}

Endpoint B
    body.user_id

Endpoint C
    body.resource.owner_id

Endpoint D
    header/object-reference

Endpoint E
    opaque_resource_token

Endpoint F
    non-obvious object reference
```

每个样本只回答：

> **“这里的值是否代表一个受保护对象引用？”**

先不回答：

> “它能不能越权？”

这是为了把：

```text Object Recognition
```

和：

```text Authorization Verification
```

严格拆开。

# 13. EXP-01 成功后的决策树

```text id="j4wb5o"
Object Reference 实验通过
        ↓
确认需要保留该机制
        ↓
进入 Authorization Baseline

Object Reference 实验不通过
        ↓
不建立新契约
        ↓
继续保留现有 heuristic
        ↓
寻找其他外部方法
```

这非常重要：

> **实验失败时，不需要“想办法让它通过”。**

失败本身就是研究结果。

# 15. 当前唯一下一动作

根据你要求的“单步工程协作”，下一步不应该四个实验一起做。

### 当前唯一下一动作：

> **只把 EXP-01：Object Reference Validation 进一步定义成一份“可直接执行但还不执行”的实验规格，包括测试输入表、变量定义、预期分类、通过/失败判据和证据记录字段。**

等这份实验规格确定后，下一轮才允许真正执行实验。

目前我们还没有进入编码阶段，也没有证据表明需要新增 `ObjectReference` 类型。

这个顺序会让后续每一次架构变化都有证据，而不是靠经验猜。
