你的判断里有一个非常关键的方向变化：**现在最危险的事情不是“代码写得慢”，而是我们在缺乏实战经验的情况下，自行发明安全研究方法、攻击策略和 Agent 控制逻辑。** 这很容易产生“能运行但不可靠”的系统。

所以这次真正应该做的，不是继续沿着原规划机械实现，而是先建立一个**外部成熟方案 → 机制提取 → Invar 映射 → 最小实验 → 再决定吸收**的研究路线。你给出的《外部技术内容深度解剖与工程吸收分析协议》本身也明确要求区分事实、作者声称、社区解释、推导和未证实假设，并优先寻找“最小有效机制”，而不是直接重构。 

下面我按照这套协议，对 **Claude-Red + Tencent AI-Infra-Guard + 当前 Invar** 做一次工程级解剖。

---

# 1. 一句话理解

### Claude-Red

它解决的是：

> **“一个没有丰富红队经验的 LLM，怎样获得某个具体漏洞类型的成熟攻击方法论，而不是临场瞎想？”**

它本质上不是漏洞扫描器，而是一个**安全专家知识与操作流程库**：把 SQLi、IDOR、SSRF、业务逻辑、Race Condition 等领域的方法论，压缩成可按需加载的 `SKILL.md`。技能通过描述触发，并提供完整检查流程、工具、边界条件和报告方法。([GitHub][1])

### AI-Infra-Guard

它解决的是：

> **“怎样把 AI Agent 安全测试从一个模型聊天过程，变成一个可运行、可调度、可报告、可扩展的扫描平台？”**

它已经不是知识库，而是完整的**执行平台 + Agent 扫描框架 + Skill 检测体系 + 规则库 + Task 管理 + 报告系统**。最新公开版本为 v4.6.2，2026-09-17 发布。([GitHub][2])

### Invar

你现在真正缺的，其实不是再造一个扫描框架。

你当前已经有：

```text
ThreatModel
CoverageUnit
Hunter
SandboxExecutor
Evidence
InvariantEvaluator
VerificationGate
PromotionGate
ResearchTask
ResearchResult
```

也就是说，**Invar 已经在“确定性执行与裁决层”投入了大量设计**。交接快照也明确把当前阶段定义为第一个标准化研究技能闭环，目标是把研究 Skill 和 Invar 的确定性安全核心连接起来。

所以三者实际上是三个不同层次：

```text
Claude-Red
    ↓
专业知识 / 方法论 / Checklist

AI-Infra-Guard
    ↓
Agent 控制 / 扫描编排 / 动态执行 / Skill Worker

Invar
    ↓
确定性 Harness / Evidence / Invariant / Verification
```

这个关系非常重要。

# 2. 内容本质

## Claude-Red 是什么？

**是安全专家经验的结构化知识层。**

它不是传统意义上的“程序”。

它最核心的产物不是 Python、Rust，而是：

```text
SKILL.md
    ↓
Trigger / Description
    ↓
Quick Workflow
    ↓
Technique Clusters
    ↓
Edge Cases
    ↓
Tools
    ↓
Testing Methodology
    ↓
Reporting
    ↓
References
```

当前 README 把它定义为按攻击面拆分的 `SKILL.md` 专家技能库，并强调技能应该按需加载。当前仓库已经覆盖 Web、Auth、Wireless、Cloud、Mobile、Exploit Development、Fuzzing、AI Security 等很多类别。([GitHub][1])

更重要的是，它的贡献规范不是“AI 随便生成一点 Markdown”。

维护规则明确要求：

* 一个 Skill 只负责一个攻击面；
* 必须有 YAML frontmatter；
* 技术内容必须可以追溯到来源；
* 要链接 CVE、公告、原始研究；
* 不允许硬编码真实受害目标；
* **明确不接受没有人工审查的 AI-generated skills。** ([GitHub][3])

这一点非常值得 Invar 学。

---

## AI-Infra-Guard 是什么？

它实际上是一个经过多轮演化的**扫描平台**。

它的架构并不是一开始就设计好的“大而全”：

```text
v0.1
纯规则型基础设施扫描
        ↓
v2.6
基础设施扫描 + MCP LLM Code Audit
        ↓
v3.6+
多模块 AI Red Teaming Platform
```

官方架构演化文档明确描述了这条路线。([GitHub][4])

到了现在，它的结构大致是：

```text
Go Backend
│
├── Task Manager
├── Agent Manager
├── Rule Engine
├── HTTP / WebSocket
└── Report / Persistence
       │
       ├───────────────┐
       ↓               ↓
Agent Scan         MCP Scan
       ↓               ↓
Python Agent       Python Agent
       ↓
Skills
       ↓
LLM
       ↓
Reviewer
       ↓
Structured Report
```

同时它把规则与知识数据从代码中分离出来，通过 YAML / Dataset 进行维护。这种“规则即数据”的思路，是它架构中很重要的一部分。官方架构文档明确把 Rule/Data Layer 作为独立层，并描述了 rule-first、LLM-augmented 的演化方向。([GitHub][5])

([GitHub][6])

# 4. Claude-Red 的“最小有效机制”

不是 Markdown。

甚至也不是“拥有很多 Skill”。

真正有效的最小机制是：

> **把安全研究专家脑中的隐性工作流，转化成 LLM 可以逐项执行的显式 Checklist。**

即：

```text
经验
↓
步骤化
↓
约束化
↓
Skill
↓
LLM 按步骤执行
```

这恰好击中了你现在遇到的问题：

> 我们没有足够实战经验，模型也没有可靠实战经验。

所以不能让：

```text
LLM
↓
“请自行研究 IDOR”
```

而应该：

```text
成熟外部知识
↓
标准化 Skill
↓
LLM 负责局部推理
↓
确定性 Harness 执行
```

这就是第一个非常重要的迁移原则。

真正核心是：

```text
任务
↓
阶段
↓
专门 Worker
↓
工具
↓
Skill
↓
模型决策
↓
结果
↓
```

当前 Agent-Scan 已明确划成：

```text
        ↓
```

并把不同安全类别拆成独立 Skill Worker，例如：

这实际上解决了一个经典问题：

> **“一个 Agent 不应该同时扮演侦察、攻击、判断和审计者。”**

它把工作拆开了。

# 6. A.I.G 最重要的设计：Skill 不是知识库，而是执行单元

这一点对 Invar 特别重要。

AI-Infra-Guard 的 `agent-scan` 本身也采用 `SKILL.md`。

其中 `authorization-bypass-detection` 的设计就是：

```text
适用条件
↓
攻击思路
↓
Dialogue
↓
观察结果
↓
判定
```

也就是说：

```text
Skill
   ↓
并不是“给模型看的一篇文章”
   ↓
而是“一个有限职责的检测策略”
```

这是 A.I.G 与 Claude-Red 最大的区别之一。

Claude-Red：

```text
Skill = 专家知识
```

A.I.G：

```text
Skill = 检测策略
```

而 Invar 最终可以形成：

```text
Skill = 检测策略描述
       ↓
Typed ResearchTask
       ↓
Deterministic Harness
       ↓
Evidence
       ↓
Invariant
```

这个结构非常自然。

# 7. A.I.G 的第二个关键机制：阶段隔离

A.I.G 并不是：

```text
一个巨大 Agent
    ↓
什么都干
```

而是：

```text
Recon
    ↓
Detection Workers
    ↓
Review
```

这对应你们之前一直强调的：

> 高内聚、低耦合、职责边界。

而 Invar 已经存在类似基础：

```text
CoverageCritic
    ↓
Hunter
    ↓
Evidence
    ↓
Candidate
    ↓
Verifier
```

所以这里**千万不要把 A.I.G 的整个架构搬进来**。

因为 Invar 本身已经有一套相似但更确定性的结构。

应该吸收的是：

> **“为什么把研究任务拆成阶段和职责”**

而不是：

> “把 A.I.G 的 Python Agent Framework 整套复制过来。”

# 8. A.I.G 最重要的工程机制：Provider Adapter

它不会要求所有目标都长成同一种 API。

官方 Agent-Scan 支持 HTTP、Dify、Coze、OpenAI、Anthropic、Google、WebSocket 等多个 Provider，并把连接方式封装为 provider configuration。([GitHub][8])

这解决的问题其实非常基础：

```text
研究逻辑
≠
目标通信协议
```

即：

```text
Research Skill
       ↓
Provider Adapter
       ↓
Target
```

这其实与 Invar 的抽象方向高度一致：

```text
ResearchTask
       ↓
Executor
       ↓
Concrete Target
```

因此这属于**高度可迁移机制**。

# 9. A.I.G 的第三个关键机制：测试靶场

这个我认为比 Agent Framework 本身更值得我们学习。

A.I.G 不只是写：

> “本系统可以发现授权绕过。”

它真的维护故意存在漏洞的 testcase。

例如：

```text
Case 2
Memory Heist Agent

Case 3
Vulnerable Customer-Service Agent
```

README 对测试目标、启动方式、预期发现结果都有明确描述。([GitHub][8])

这意味着：

```text
Scanner
+
Vulnerable Target
=
可重复实验
```

这才真正把：

```text
“感觉我们的 Agent 会发现漏洞”
```

变成：

```text
“我们有一个已知漏洞靶场，可以重复验证 Scanner 是否发现。”
```

这与我们当前的工程哲学几乎完全一致：

> 证据先于实现、测试先于交付。

而我们的当前体系已经有 Sandbox / Verification / Evidence，因此这个思想甚至可以和 Invar 非常自然地结合。

# 10. 最值得吸收的东西其实是“证据问题”

这里出现了一个非常重要的反直觉结论：

## A.I.G 很成熟，但不能把 A.I.G 当成真理机器。

因为它自己也还在解决：

> **evidence-free false positives**

2026-09-17 的 v4.6.2 更新里明确包含：

```text
Reduce evidence-free false positives
Reconcile verdicts with public findings
Prevent model tool-call stalls
```

([GitHub][9])

这恰恰证明：

```text
LLM Detection
≠
可靠漏洞事实
```

也就是说，你们目前“Evidence Contract / Verification Gate / Promotion Gate”的方向并没有被外部项目推翻。

反而被 A.I.G 的实际迭代经验进一步验证了：

> **Agent 负责寻找证据，不能直接定义事实。**

# 11. A.I.G 自己踩过的坑，对我们尤其有价值

这个地方非常值得认真看。

### 坑 1：扫描器自己的观察窗口被攻击者绕过

2026 年 8 月，有安全问题指出 A.I.G Skill Scanner 的 Agent 工具把：

```text
__pycache__
.pyc
.pyo
```

主动隐藏。

于是一个运行时可达的恶意 Python payload 可以躲过 LLM 对源码树的观察。([GitHub][10])

这说明：

```text
Agent 只能看到什么
=
Scanner 实际能证明什么
```

这是极其重要的设计原则。

---

### 坑 2：路径边界检查错误

另一个公开问题指出，其部分文件工具使用：

```text
path.startswith(base_dir)
```

进行路径包含关系判断。

这在：

```text
/tmp/skill
/tmp/skill-evil
```

这种情况下会产生错误通过。([GitHub][11])

这再次说明：

> **Agent 工具边界必须由 deterministic code 强约束。**

不能：

```text
Prompt:
“请不要访问目录之外的文件。”
```

而应该：

```text
Tool
↓
Path Canonicalization
↓
Boundary Check
↓
Execution
```

这和你们的 Rust 强类型 / 目录边界 / Deterministic Harness 原则高度一致。

# 12. A.I.G 自己也证明了“规则 + LLM”比“全 LLM”更合理


([GitHub][4])

这个结构和 Invar 的方向非常一致。

# 15. 现在我认为最重要的一个结论

## 我们不应该继续“原创安全方法论”。

这不是说我们永远不要创新。

而是：

> **在安全研究知识层，当前阶段优先采用成熟公开方法论；在系统工程层，继续保留 Invar 自己的确定性核心。**

这两个层次必须分开。

### 错误路线

```text
我们没有实战经验
↓
自己设计 IDOR 方法
↓
自己设计验证算法
↓
自己设计 Agent Loop
↓
自己设计 Evidence 判定
↓
出现大量特殊情况
↓
补丁
↓
架构越来越复杂
```

### 更合理的路线

```text
成熟外部项目
↓
提取成熟安全知识
↓
形成 Skill
↓
映射为 Invar ResearchTask
↓
确定性 Harness 执行
↓
Evidence
↓
Verification
↓
实验
↓
只有发现真实缺口才创新
```

这实际上更符合你们自己的“根因 > 补丁 / 复用 > 重造 / 验证 > 猜测”的工程宪法。

# 16. Claude-Red 最值得吸收的 5 个思想

### 第一：一个 Skill 一个研究面

Claude-Red 明确强调：

> One skill, one surface.

而不是一个 Skill 里面塞所有 Web 安全知识。([GitHub][3])

这与 Invar 的 CoverageUnit 天然契合。

---

### 第二：知识必须来源可追溯

Claude-Red 要求：

> Cite sources.

并要求技术内容可追溯到 CVE、研究论文、公告等来源。([GitHub][3])

这个机制非常适合进入 Invar 的 Knowledge / Provenance 层。

---

### 第三：Skill 应该是执行顺序，不是百科全书

真正有价值的是：

```text
Preparation
→ Baseline
→ Identification
→ Test
→ Bypass
→ Verification
→ Reporting
```

而不是：

```text
“什么是 IDOR？”
```

---

### 第四：成熟知识也必须允许“不适用”

IDOR Skill 明确把：

```text
角色
多账户
对象 ID
读写操作
上下文权限
```

作为适用条件。

这避免了：

```text
所有目标
→ 强行测试 IDOR
```

这一点尤其重要。

---

### 第五：AI 只是知识载体，不是知识来源

Claude-Red 自己明确表示，AI 生成的 Skill 需要人工审核。([GitHub][3])

这对于我们非常关键。

```text
Scanner
=
可重复验证
```

---

### 第五：工具必须承担安全边界

不是：

```text
Prompt 告诉 Agent “别乱来”
```

而是：

```text
Tool
↓
Permission
↓
Boundary
↓
Execution
```

A.I.G 自己出现的 `.pyc` 可见性问题和路径包含问题，实际上正好说明这一层的重要性。([GitHub][10])

# 18. 哪些东西不要照搬

这是这次研究最重要的“反向结论”。

## 不要把 Claude-Red 整个复制进 Invar

因为：

```text
Claude-Red ≈ Knowledge Corpus
```

它不是你的执行引擎。

直接搬几百个 Skill，会迅速造成：

```text
Skill 爆炸
Prompt 上下文膨胀
触发规则混乱
重复方法论
维护困难
```

真正应该吸收的是：

```text
Skill Format
+
Methodology
+
Sources
+
Workflow
+
Scope
```

而不是整个目录原样塞进去。

---

## 不要把 A.I.G 的整个 Agent Framework 搬进 Invar

因为 Invar 已经拥有：

```text
Harness
Evidence
Invariant
Verification
Promotion
```

如果再把：

```text
A.I.G Agent
+
Tool Dispatcher
+
Worker
+
Reviewer
+
Task Manager
```

整体搬进来，很可能出现：

```text
Invar Executor
+
AIG Executor
+
两个 State Machine
+
两个 Evidence Model
+
两个 Report Model
```

这正是你最开始担心的：

> 为了解决一个问题，制造另外十个问题。

# 19. 更危险的一点：外部项目也会踩坑

这两个项目不能成为：

> “别人已经证明正确，所以我们复制就行。”

证据恰恰不支持这个结论。

A.I.G 在 2026 年仍然持续修复：

```text
evidence-free false positives
tool-call stalls
incomplete scans
path validation
file visibility
```

([GitHub][9])

所以真正应该吸收的是：

> **成熟项目已经经历过哪些坑，以及它为什么最后这样设计。**

这比复制代码重要得多。

# 20. 一个非常值得警惕的外部项目内部不一致

A.I.G 当前 GitHub 首页、LICENSE、NOTICE 明确显示项目现在采用 **Apache License 2.0**，并要求保留 LICENSE/NOTICE、进行产品署名等。([GitHub][12])

但它仓库里的 `CODEBUDDY.md` 仍然写着：

> Licensed under MIT.

([GitHub][13])

这是非常好的工程研究案例：

```text
外部项目 ≠ 完美权威
```

即使是成熟大型项目，也可能出现：

```text
代码
文档
开发指南
License metadata
```

之间不同步。

所以以后我们的外部项目吸收流程必须增加：

```text
源码
+
CHANGELOG
+
LICENSE
+
Issues
+
PR
+
README
```

多源交叉验证。

这和你给出的分析协议要求也是完全一致的。


当前架构已经有：

```text

       ↓

       ↓

       ↓

       ↓

       ↓

       ↓

       ↓
```


因此真正缺失的拼图是：

这个方向与当前交接中 R2-1 要建立的第一个授权研究 Skill 正好一致。

# 24. 最小验证实验

这里我不建议马上改代码。

我们现在最值得做的实验只有一个：

## Hypothesis

> **把 Claude-Red 的成熟 IDOR 方法论 + A.I.G 的授权绕过检测思想，整理为一个受控 Skill 后，能够在不改变 Invar Deterministic Core 的前提下，提高研究路径覆盖率，并减少 LLM 临场发挥。**

## Baseline

当前 Invar：

```text
Research Task
→ 当前已有 Hunter / Sandbox
```

不额外引入外部方法论。

## Variable

**唯一变量：**

加入一个经过来源标注、范围明确的 Authorization / IDOR Skill。

不修改：

```text
Sandbox
Evidence
Invariant
Verification
Promotion
```

## Metrics

至少记录：

```text
研究步骤覆盖数
已执行检查项数量
重复尝试数量
获得 Evidence 数量
有效 Candidate 数量
无结论 / Blocked 数量
LLM 调用次数
```

如果以后有本地故意漏洞靶场，再增加：

```text
True Positive
False Positive
Missed Finding
```

## Expected Result

如果外部方法论真的有效：

```text
相同 Harness
+
更成熟 Skill
↓
研究覆盖率提高
重复尝试下降
Evidence 数量提高
```

## Falsification Condition

如果：

```text
覆盖率没有提高
或
Evidence 没有增加
或
重复操作反而增加
或
LLM 被 Skill 诱导到大量无效路径
```

那么这个 Skill 就不是值得迁移的机制。

这完全符合你提供的“一变量、一实验、一结论”原则。

```text
知识来源
```

```text
Research Steps
↓
Candidate Experiments
↓
ResearchTask

Harness
```

### ④ Testcase 应该成为一等公民

A.I.G 给我们的最大工程启发之一不是 Agent，而是：

> **每一种重要研究能力，都必须有可重复验证的已知结果靶场。**

### ⑤ 外部项目的失败案例也是资产

比如：

这些不是“别人写得不好”的故事。

> **Invar 设计测试用例的素材库。**

# 26. 最终研究结论

## Q1：真正值得学习的东西是什么？

**Claude-Red：成熟安全专家知识的结构化方式。**

**AI-Infra-Guard：把这些知识变成可执行扫描流程的工程组织方式。**

**而 Invar：应该负责最后的确定性事实裁决。**

---

## Q2：底层原理是什么？

整个体系最后可以压缩成：

```text
经验知识
↓
结构化方法论
↓
有限研究动作
↓
真实执行
↓
观察结果
↓
Evidence
↓
Verification
↓
Conclusion
```

而不是：

```text
LLM
↓
“我觉得这是漏洞”
```

---

## Q3：哪些与当前 Invar 高度相关？

最高度相关的是：

```text
Skill
Checklist
Preconditions
Provider Adapter
Stage Separation
Evidence
Verification
Testcase
Tool Boundary
```

尤其是：

> **Skill + Testcase + Deterministic Harness**

这三个组合。

---

## Q4：哪些看起来先进，但没有必要引入？

现阶段没有必要整体引入：

```text
A.I.G 完整 Server-Agent 平台
A.I.G 完整 TaskManager
A.I.G 完整 WebUI
A.I.G 完整 Agent Runtime
多套重复 State Machine
第二套 Evidence System
第二套 Finding System
```

因为这些能力 Invar 已经存在或者有自己的方向。

---

## Q5：现在最值得马上做的一个最小验证实验是什么？

**不要重构。**

先做：

> **把 Claude-Red 的 `offensive-idor` + A.I.G 的 `authorization-bypass-detection` 做一次“方法论交叉提取”，只形成一个 Invar Authorization Research Skill 草案，然后让它在现有 Invar Harness + 本地已知靶场上跑一次基线/实验对比。**

不动：

```text
Rust Core
Sandbox
Evidence
Invariant
Verification
Promotion
```

只改变：

```text
Research Knowledge
```

这样一旦实验结果证明：

```text
外部知识
→
更高覆盖率
→
更多可验证 Evidence
→
更少无意义尝试
```

我们再把这个模式推广到：

```text
IDOR
Business Logic
SSRF
Auth Bypass
Race Condition
...
```

## 最后一个非常关键的判断

我现在不会把这两个仓库定义成：

> “别人写得比我们好，所以我们把 Invar 改成他们。”

更准确的定义是：

```text
Claude-Red
= 安全知识基准

AI-Infra-Guard
= Agent 安全执行基准

Invar
= 确定性研究与证据基准
```

**真正应该做的是三者拼接，而不是三选一。**

而且这次研究已经暴露出一个非常明确的方向：**我们当前最可能真正缺失的不是新的算法，而是一个经过外部实战知识校准的 Research Skill / Knowledge Layer。**

这与当前交接中 R2-1 的目标恰好重合。

我建议下一步先不要写代码，而是把这两个仓库中的 **Authorization / IDOR 相关 Skill 原始材料做一次“逐段交叉解剖”**，直接产出一份 **`Claude-Red IDOR ↔ A.I.G Authorization Bypass ↔ Invar ResearchTask` 三方机制矩阵**，那会比现在直接创建 `SKILL.md` 更稳。
